## Missing context

Three real gaps surfaced while building this unit, all recorded in
`model.md`'s Model drift log and `build-plan.md`'s Coverage table, not just
here — this section is the origin, those are the propagated record:

1. **`test_self_md_appears_in_self_frame` and `test_self_md_absent_from_ls_listing`
   were contracted against features that don't exist yet** (`frame()`
   integration, `ls()`). Neither is owned by U-002. Implemented against what
   this unit actually controls instead: `RebuildResult.self_content` (proves
   available) and a direct query of the `blocks` table (proves absent) — the
   promise each name makes is still genuinely tested, just not through the
   not-yet-built surface the name implies.
2. **Wiring `self.md` into `frame('self', ...)` has no owning unit anywhere
   in `build-plan.md`.** This is a real coverage gap, not a rename — added
   to build-plan.md's Coverage table for the user's attention.
3. **Graph-edge reconstruction on rebuild isn't possible with the current
   block format.** U-001's frontmatter has no field for encoding an edge to
   another block. Descoped from this unit's Done-when (which originally
   claimed edge-row parity); consistent with — and now explicitly extending
   — model.md's already-disclosed α/β-loss-on-reindex trade-off.

One design decision made and worth surfacing even though it wasn't
blocking: **rebuild assumes an empty `blocks`/`block_tags`/`edges` table
set as a precondition** (documented in the module's own docstring) rather
than doing incremental upsert-and-reconcile. Reason: `block_outcomes` and
`edges` cascade-delete on `blocks.id`, so a delete-then-reinsert rebuild
strategy would silently destroy outcome history even for blocks whose id
didn't change — pure-insert-into-empty-tables avoids that trap entirely, at
the cost of requiring the *caller* (not yet built — belongs to whatever
CLI/API surface invokes this) to wipe or recreate `index.db` first for a
true full rebuild.
