## Missing context

**One real design decision, not left implicit**: uses `hybrid_retrieve()`
(the pure retrieval stage) rather than the higher-level `recall()`.
`recall()` reinforces returned blocks and co-retrieved edges as a
side effect — calling it against the "before" database to capture a
baseline would mutate that database mid-comparison, and calling it twice
(once per side) would make the second call's results depend on what the
first call already changed. A parity *gate* has to be read-only or its own
act of checking invalidates the check. Not a deviation from the "named"
contract — this is exactly the kind of detail deferred to the pass that
builds the unit at full depth.

**Test design note, not a code issue**: the first attempt at
`test_diverging_query_results_fail_the_gate` used different *content*
between before/after for the same block id, expecting the ranking to
diverge. It didn't — with only one candidate block in the fixture, it's
always the top (only) result regardless of content, and separately, mock
embeddings are content-hash-derived rather than semantically meaningful, so
there's no reliable way to make one string "more similar" to a query than
another in the fixture. Rewrote using two blocks with **swapped confidence**
between before/after instead — same block count, same content, different
evidence — which is actually a more realistic failure mode for this gate to
catch (scrambled α/β during a botched migration) than content drift would
have been.

**What this unit deliberately does not do, per its own contract**: run
against the real production database. Everything above is verified against
synthetic fixtures. Actually running the migration — export the real
`~/.elfmem/databases/elfmem.db`, rebuild, and check parity — is a distinct,
explicit action for whoever operates the real migration, not something
building this mechanism performs on its own.
