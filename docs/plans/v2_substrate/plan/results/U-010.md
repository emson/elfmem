**The user resolved the fork-vs-depend question directly** (open decision 5)
— forked, per the recommendation, to avoid the cross-project coupling and
because `ctx`'s read-only-vault invariant won't hold once `elf-review` needs
write access later.

**Scope was deliberately narrowed from the full `ctx` skill**, and this is a
real judgment call worth surfacing rather than treating as obviously correct:
only Find mode was ported (Discover → Judge → Worksheet). `ctx`'s Compile
mode (assembling curated excerpts into an LLM-ready prompt), Session mode
(handoff capture), and Attach/Init mode (multi-vault configuration) were all
left out — none has a demonstrated need against the research doc's actual
description of `elf-recall`'s job ("occasional, human-supervised, unranked
retrieval"), and porting them speculatively would have been exactly the
"additive, however central it feels" mistake the sequencing guide warns
against. If a real need for Compile mode shows up, it's a small addition on
top of what exists, not a redesign.

**One vocabulary simplification from the original**: dropped the
`freshness` field ctx's judge vocabulary has. ctx's free-form vault has no
reliable timestamp to judge against; elfmem blocks already carry a real
`created:` frontmatter date (U-001), so a judge's freshness *guess* would be
redundant with — and could silently contradict — data the block already
states.

**Open, not resolved**: where this skill physically ships for a real elfmem
user to install (currently at `skills/elf-recall/` at the repo root, not
inside `src/elfmem/` since it isn't Python package code) is a packaging
question with no answer yet — how would a user of the published `elfmem`
package get this into their own project's `.claude/skills/`? Flagged, not
blocking Wave 3's remaining unit.
