# Migration dry run — 2026-08-10

**What this is**: a read-only rehearsal of the real migration (U-004 export →
U-002 rebuild → U-005 parity gate) against a copy of the actual production
database. Nothing here touched `~/.elfmem/databases/elfmem.db` — verified by
MD5 before and after (`13963ed526426f781982615b289043ae`, unchanged) and by
opening the copy under SQLite's `mode=ro` URI flag (`PRAGMA query_only=ON`),
a second enforcement layer beyond the filesystem `chmod 444` already applied
to the copy.

Script and artifacts: `/private/tmp/.../scratchpad/v2-migration-dryrun/`
(session-scratch, not part of the repo).

## Round 1 — before the fix

```
Baseline: active=140 inbox=3 archived=42 (185 total)
Exported: 185 blocks -> 11 files
Rebuilt: 158 blocks written  <-- should have been 143 (140 notes + 3 log)
Block count: before=140 after=155  MISMATCH
Query parity: 5/5 DIVERGE
GATE PASSED: False
```

**Diagnosis**: 158 vs. expected 143 is 15 extra blocks. Per-category
comparison against the real DB's `GROUP BY category, status` counts isolated
it to exactly two categories — `mind` (3 real blocks → 15 parsed headings)
and `message` (30 real → 33 parsed). Inspecting one `mind` block's actual
content confirmed the cause: Theory-of-Mind blocks are themselves structured
documents (`# Mind Model: X\n\n## Goals\n...\n\n## Beliefs\n...`), and
`parse_blocks` treated every `##` line — including these legitimate
sub-headings — as a new block boundary.

**Fixed** in `src/elfmem/memory/blockfile.py` (see `results/U-001.md`'s
post-hoc fix section for the full before/after and the two new regression
tests). Full elfmem suite re-verified green (1,211 passed / 3 skipped)
before re-running the dry run.

## The remaining divergence is expected, not a new bug

All 5 fixed queries still show different top-5 rankings before vs. after.
This is **not** the same class of problem as the parser bug — it is the
already-documented, already-accepted trade-off from the very first version
of this plan (companion plan doc §10 residual risks: *"Losing α/β and
reinforcement history on reindex... medium likelihood, low impact... only 6
outcomes exist to lose"*), now empirically visible on the real corpus for
the first time:

1. **Graph edges are not reconstructed on rebuild** (model.md's Model drift
   log, first entry) — centrality scoring, part of the composite ranking,
   necessarily changes.
2. **Reinforcement count and recency (`last_reinforced_at`) are not carried
   through export → rebuild.** `U-004` doesn't export them and `U-002`'s
   `_write_block` doesn't consult `Block.extra` for them even where U-004
   *did* export related fields.
3. **Confidence/α/β specifically**: `U-004`'s export *does* write
   `confidence`/`alpha`/`beta` into each block's `extra` frontmatter fields
   — but `U-002`'s rebuild never reads them back; every rebuilt block gets
   `insert_block`'s hard-coded default (`confidence=0.5`) regardless of what
   was exported. This is the one piece of the three that could cheaply be
   closed (the data is already sitting in the file, unused) without touching
   the harder edges/reinforcement trade-offs.

None of this is a defect in what was built — U-002 and U-004 did exactly
what their contracts said. It's a real, now-quantified answer to a question
the plan always flagged as open: **how much does retrieval actually change
after a naive rebuild, on this specific corpus?** Answer: every one of 5
representative queries reorders in the top-5, though the block sets
overlap substantially rather than being wholesale different (e.g. the
`attention`/`memory consolidation` query keeps 3 of 5 ids, reordered plus
one substitution).

## What this means for U-006

Phase 4's gate is doing its job — it correctly reports `False` given the
current build's scope, and the plan doc's own instruction is explicit:
*"do not proceed on the assumption that a diverging ranking is probably
fine."* Three live options, in ascending cost:

- **Accept it as already-scoped**, same as the original plan intended, and
  proceed to Phase 5 (hand-restore) treating this level of reordering as
  the known cost of the migration.
- **Wire `U-002` to consume `extra["confidence"/"alpha"/"beta"]` on
  rebuild** — cheap (the data already round-trips through the file, U-002
  just isn't reading it), would likely narrow the divergence, would not
  eliminate it (edges and reinforcement/recency remain unaddressed).
  Retest the dry run after, on this same corpus, to see how much it helps
  before deciding whether it's worth doing for real.
- **Investigate further** — e.g. check whether the reordering is
  qualitatively acceptable (still-relevant blocks, just resorted) or
  actually surfaces worse results, before deciding.

Not decided here — this is exactly the kind of call the plan's own gate
exists to route to a human, not resolve silently.
