## RRF (Reciprocal Rank Fusion, Cormack et al. 2009) replaced n
<!-- id: 44e470a1e0afd5f5  cls: project  tags: [bug/rrf-old-dedup, design/retrieval, design/rrf]  pinned: false  created: 2026-04-27T12:09:10.870980+00:00 -->
cue:: debugging keyword matches ranking badly, or tuning fusion of BM25 and vector similarity scores

RRF (Reciprocal Rank Fusion, Cormack et al. 2009) replaced naive BM25 dedup in PR #32. The old approach appended BM25-only hits with similarity=0.0, actively penalising keyword hits in composite scoring. RRF merges both ranked lists: rrf(block) = Σ 1/(k + rank), k=60. Scores normalised to [0.0, 1.0]. Blocks found by both rankers score higher. When BM25 is empty or all-zero, raw cosine similarity is preserved unchanged.

## Hebbian co-retrieval (C1): blocks that co-appear in frame()
<!-- id: 37ba0db42a0fd92d  cls: project  tags: [bug/hebbian-cache, bug/hebbian-zombie, design/graph, self/constraint, self/context]  pinned: false  created: 2026-04-27T12:09:10.885132+00:00 -->

Four critical fixes discovered via agent simulation: (1) SELF frame 1h TTL cache was triggering staging on cache hits — guard: if not result.cached. ## **Release Workflow for elfmem (v0.11.0 release)**
<!-- id: 3c55ba8078a48739  cls: project  tags: [automation, elfmem-specific, git, pypi, release-workflow]  pinned: false  created: 2026-05-03T12:01:07.858244+00:00 -->
cue:: cutting an elfmem release - version bump, changelog date, git tag, PyPI publish

**Release Workflow for elfmem (v0.11.0 release)**

**Steps (in sequence):**

1. **Feature branch development** — Implement features, commit normally, create/update PR

2. **Version bump (on feature branch)**
   - Update `pyproject.toml` line 7: `version = "X.Y.Z"`
   - Update `CHANGELOG.md`: change `## [Unreleased]` to `## [X.Y.Z] — YYYY-MM-DD` (today's date)
   - Commit: `git commit -m "chore: release vX.Y.Z"`
   - Push to feature branch: `git push origin feature-branch`

3. **PR merge** — Review, approve, merge to main via GitHub

4. **Tag on main** (post-merge)
   - `git fetch origin && git checkout main && git reset --hard origin/main`
   - `git tag -a vX.Y.Z -m "Release X.Y.Z"`
   - `git push origin vX.Y.Z`

5. **Automated PyPI publish**
   - GitHub Actions workflow `publish.yml` triggers on tag `v*.*.*`
   - Runs: `pytest` (3.11, 3.12) → `uv build` → `uv publish --trusted-publishing always`
   - Uses OIDC (no credentials needed)
   - Do NOT run `uv publish` locally

**Patterns observed:**
- SemVer: patch (bug fix) / minor (new features) / major (breaking)
- CHANGELOG format: one bullet per logical change, clear language
- Git workflow: tag is the release trigger, not the merge
- CI publishes automatically (pre-push hook ensures tests pass before tag)
- Merge conflicts in CHANGELOG need manual resolution (both branches edit [Unreleased])

**Fail-safe: cleanup dist/ before building**
- Old versions in `dist/` directory cause `uv publish` to attempt uploading all files
- `rm dist/elfmem-*.tar.gz dist/elfmem-*.whl` before `uv build` to keep only current version

**Why this works:**
- Tag-driven release decouples CI/CD from branch workflow (main stays clean, tags are authoritative)
- OIDC trusted publishing avoids credential management (GitHub action has deployment token)
- Pre-push hook catches lint issues locally (ruff + mypy before reaching GitHub)
- Semantic versioning makes intent clear in git history

## Anything the system accumulates is history, not derivation —
<!-- id: fa99bc29abf09645  tags: [self/value, v2-substrate, architecture, bug-pattern, decision]  pinned: false -->
cue:: when deciding whether some piece of state should be stored or recomputed, or when a rebuild silently loses scores, summaries or graph edges

Anything the system accumulates is history, not derivation — even when it looks recomputable. This surfaced three times during the v2 substrate cutover, each time as silent data loss on rebuild: (1) decay_lambda looks like a pure function of tags, but outcome() with a negative signal multiplies it, so a penalised block carries a lambda no tag lookup can reproduce; (2) block summaries look like a cache of content, but regenerating one costs an LLM call, so discarding them leaves the whole corpus unscored; (3) similarity edges look derivable from embeddings, but consolidation scores them against *summary* embeddings and temporal proximity at promotion time, so recomputing builds a different graph rather than restoring this one. The test that catches all three: if a value was ever mutated by an event after it was first computed, it is history and belongs in the ledger.

## Test the layer the bug can actually live in, not the layer b
<!-- id: 7bfe09d29da028f5  tags: [self/value, testing, bug-pattern, mcp]  pinned: false -->
cue:: when writing a test for a wrapper, adapter or tool surface, or when a passing test failed to catch a bug that reached production

Test the layer the bug can actually live in, not the layer below it. A unit test for elfmem_remember's cue parameter passed while the tool silently discarded that cue in production: the test exercised the internal delegate _tool_remember, but the defect was in the registered @mcp.tool() wrapper that calls it. The tool accepted the parameter, published it in its schema, documented it as mandatory, returned success — and dropped it. The durable fix was structural rather than another example test: assert that every parameter a registered tool declares appears in the call to its delegate, so the whole class fails loudly instead of one instance. ## Enforcement built on a lossy measurement must bound its fals
<!-- id: 70bb508a67ea3f32  tags: [design/enforcement, design/hooks, pattern/goodhart, self/constraint, self/value]  pinned: false -->
cue:: designing a gate, nudge, or enforcement mechanism on top of attribution or another lossy signal; a hook or check that tells the model which tool to call; suspecting a feedback loop where compliance pollutes the signal being enforced

Enforcement built on a lossy measurement must bound its false-positive cost and must never prescribe its own metric as the remedy. The engagement gate's first design (sticky per-session scope, remedy message "call elfmem_recall") failed both ways: in long mechanical sessions it punished every paraphrase-only turn — the error direction lexical attribution deliberately leaves unpunishable — and a retrieval performed to satisfy a gate lands in the use ledger indistinguishable from genuine engagement, so the enforcement mechanism manufactured the exact retrieval-counting pathology record_use() exists to correct (Goodhart, self-inflicted). The redesign that held: scope the gate to the turns where the failure was actually observed (vocatively-addressed prompts only), move prevention upstream of correction (an engage-or-dismiss line injected with the context, before the answer is written), and write the remedy message to point at evidence already present while permitting "none of this applies" as an honest outcome. Stickiness rejected with a reintroduction trigger: a real engagement miss on a non-vocative follow-up turn.

## The SELF-frame salience judge for automatic memory capture a
<!-- id: 1935ae5f8d7e902b  tags: [design/capture, design/hooks, design/salience, self/constitutional, self/goal]  pinned: false -->
cue:: designing automatic memory capture, salience detection, or deciding when an agent should write to memory; asking what triggers a remember() or how to recognise memorable content in a session

The SELF-frame salience judge for automatic memory capture already exists: it is dream()'s alignment scoring. Capture design should therefore be a funnel — deterministic trigger detection in hooks (corrections, preferences, hard-won conclusions, novelty), liberal insertion into the inbox, and consolidation as the single authoritative SELF-alignment gate — never a second salience engine. Two corollaries: (1) because SELF differs per instance, identical capture code yields personalised memory per agent; (2) the trigger lexicon should be mined from real missed-capture moments (manual remember calls in transcripts) and tuned by the use signal — capture more of what record_use shows gets drawn on. Write-side capture failure is the mirror of the read-side recall failure: a soft protocol competing for attention, fixed the same way (hook-enforced, per-turn nudge, agent does the distilling).

## Retrieval's `score` field on returned blocks (frame()/recall
<!-- id: bd83935bb5743ae2  tags: [design/capture, bug-pattern, design/retrieval, self/constraint]  pinned: false -->
cue:: building a novelty, near-duplicate, or salience check and considering reusing a recall/frame result's score field instead of a fresh embedding comparison

Retrieval's `score` field on returned blocks (frame()/recall()) is a blended ranking value, not raw cosine similarity — reinforcement, recency, alignment, and an exploration bonus all factor in. It cannot substitute for the raw cosine similarity that near_dup_near_threshold (consolidation's dedup) is calibrated against, despite both living in [0,1] and both being called "score". Live-tested proof: a control query with zero semantic relation to any of 4 stored facts still scored 0.93-0.94 against every one of them in a small sandbox corpus. Any future novelty/near-duplicate check must use a real embedding call and dedup.py's actual cosine_similarity path against active-block embeddings — there is no free reuse of an already-computed retrieval score for this purpose.
