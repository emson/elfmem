## Branch hygiene after squash-merge PRs: GitHub's squash-and-m
<!-- id: 5527da69dc17726a  cls: project  tags: [branch-hygiene, bug-pattern, git, self/constraint, self/style, squash-merge]  pinned: false  created: 2026-04-28T21:58:48.230914+00:00 -->
cue:: when git shows divergent branches, stale branches, or conflicts after a squash-merged PR

Branch hygiene after squash-merge PRs: GitHub's squash-and-merge creates a new commit on main with a different SHA than the source branch's commits. This means: (a) the source branch will always show as 'ahead' of main even though the content is identical, (b) rebasing the source branch onto main will replay already-merged commits causing conflicts, (c) git pull on the source branch after merge will diverge. Rule: delete feature/release branches immediately after PR merge. Enable GitHub's auto-delete-branch setting. When multiple branches exist for the same work (e.g. fix/commits, feature/simulate, release/v0.7.0), clean up ALL of them after merge — stale branches are the #1 source of divergent-branch confusion.

## Peer design failure: silent success is the root failure mode
<!-- id: 8c7fb427a251f90e  cls: project  tags: [design, failure-mode, peer, peer-health, self/goal, self/value, silent-success]  pinned: false  created: 2026-04-30T21:35:30.513439+00:00 -->
cue:: when debugging peer send or peer inbox failing silently against default or wrong paths

Peer design failure: silent success is the root failure mode in peer communication. PeerConfig has defaults (inbox_dir: ~/.elfmem/inbox) that cause peer inbox to silently scan the wrong path and return 0 messages with no error. peer send writes to delivery_path without validating it is accessible. Both operations succeed silently when they should warn. Solutions in priority: (1) elfmem peer health command — checks DB-config consistency, inbox readability, outbox writability, delivery path accessibility per peer; (2) burn peer setup into PERMANENT SELF blocks at peer init/peer add time so sessions recall config as identity, not as files; (3) warn when peer inbox returns 0 messages but peers have been active recently; (4) DB-config drift detection comparing stored last_known_inbox_dir against current config. Key principle: invert seed direction — do not seed SELF from config, seed config facts INTO SELF at setup time, because SELF blocks survive where config files can be lost.
