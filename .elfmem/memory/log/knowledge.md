## Any operation that can silently reduce, reword, or degrade w
<!-- id: ff4980bb7ba00905  tags: [design/api, principle/agent-first, self/constraint, design/observability]  pinned: false -->
cue:: designing an API that filters, truncates, caps or rewrites what a caller supplied; deciding what a result object should report; a caller says data went missing but the call returned success

Any operation that can silently reduce, reword, or degrade what the caller intended must say so in its typed result — an empty "dropped" list is the caller's only proof that "this is everything". Corollaries learned from implementing this across elfmem's write path: (1) put the reason on each reduced item, never one scalar per call, because a single call can reduce for several independent reasons and a scalar must misreport all but one; (2) fixing a silent-reduction bug by silently overriding an explicit caller argument just moves the bug — when a guarantee conflicted with top_k, the right fix was changing top_k's DEFAULT to max(config, n_guaranteed) while keeping an explicit value a hard ceiling; (3) a diagnostic that reads through the normal retrieval path will mutate the scores it reports on, so preview modes need the side effects disabled (frame(reinforce=False)); (4) when content exceeds a budget, overrun the budget rather than truncate — cutting a principle mid-sentence can inverts its meaning ("never do X" -> "never do").

## A tag that grants a privilege in one place must not silently
<!-- id: 3e9b59365d891a84  tags: [design/frames, design/api, self/constraint, pattern/tag-privilege]  pinned: false -->
cue:: a tag or flag confers protection or priority in one subsystem; deciding whether to exclude a category of block from a frame, query or scoring path; adding a filter to a list that other code also reads

A tag that grants a privilege in one place must not silently grant privileges everywhere. `self/constitutional` was designed to grant PERMANENT decay and a guaranteed SELF slot; it also, unintentionally, granted unrestricted competition in every other frame and immunity from nothing at all — so a well-written constitution starved the ATTENTION frame (4 of 5 slots) and task P&L silently degraded identity's Beta posterior (0.50 → 0.114 over six losing trades). Two design lessons: (1) exclusion needs an exemption when the tag is machine-assignable — `self/constitutional` is applied by the consolidating LLM too, so it sits on genuine knowledge (peer letters), and a blanket exclusion deletes that; the exemption mirrors SELF's own guarantee_excludes, because the same fact ("a peer letter is knowledge, not identity") is being encoded from opposite directions. (2) When adding a guard that filters a list, check what else downstream consumes the UNFILTERED list — peer trust is computed from the full outcome() id list, so filtering there too would have silently disabled trust evolution for the exact peers whose letters carried the tag.

## When adding a filter to a pipeline, enforce it where the wor
<!-- id: 0b23b76d8242f2e3  tags: [design/pipeline, bug-pattern, self/constraint, design/retrieval]  pinned: false -->
cue:: adding a filter, exclusion or guard to a multi-stage pipeline; a filtered item still appears in output; deciding whether to patch each entry point or enforce once

When adding a filter to a pipeline, enforce it where the working set is FINAL, not only at the entry point — and check every stage that can introduce items independently. elfmem's retrieval excluded blocks at the stage-1 prefilter, but stage 3 (graph expansion) fetches a seed's neighbours from the database by id, so excluded blocks walked back in behind the filter and were both "excluded" and rendered simultaneously. Two generalisable points: (1) the worst leaker is often the item the filter most wants to stop — a constitutional block is excluded precisely because it is central and well-connected, which is exactly what puts it in reach of graph expansion; (2) prefer one choke point over patching each entry site, because a future stage that introduces items cannot bypass a choke point but will silently bypass a per-site patch (three enforcement sites for one invariant is the smell). Keep the entry-point filter as an optimisation, and mutation-test the split: removing the choke point should break correctness while removing the prefilter should break nothing.

## Before shipping a migration, measure round-trip fidelity fie
<!-- id: 31894ba8d94068ae  tags: [design/migration, self/constraint, pattern/verification]  pinned: false -->
cue:: designing or reviewing a data migration, a storage-format cutover, or a irreversible-seeming config flip; deciding what to verify before trusting a migration

Before shipping a migration, measure round-trip fidelity field-by-field rather than trusting a behavioural gate. elfmem's substrate migration had a retrieval-parity gate (rankings match on 4 frame queries), which is necessary but not sufficient for a cutover decision — it would not have caught lost cues, categories, amendments or edges. A direct state diff (export → rebuild → compare every column and tag) proved zero drift and was what actually justified building the cutover. Two design rules that fell out: (1) a cutover/flip step is safe to offer only when it is reversible by construction — here the DB is still written under file authority, so flipping back leaves it complete, which turns an irreversible-looking decision into a config edit; (2) preflight must report EVERY failing condition at once, never short-circuit, or you rebuild the "each fix revealed the next gate" experience one round trip at a time.

## A config value can be "wired correctly" at 3 of 4 call sites
<!-- id: 002470ddaf57edba  tags: [bug-pattern, design/config, self/constraint, pattern/partial-wiring]  pinned: false -->
cue:: a config value seems unused at one call site despite being wired elsewhere; deciding whether a naming/identity gap is a real bug or just underdocumented; auditing whether a field reaches every place it should

A config value can be "wired correctly" at 3 of 4 call sites and still produce a live bug at the one that matters most — grep for every hardcoded literal the field was supposed to replace before trusting that a field "existing and being used elsewhere" means it's fully wired. elfmem's `project.agent_name` was genuinely used by init/doctor/AGENT.md generation, which made it easy to assume the SELF frame's runtime preamble read it too — it didn't; `_SELF_PREAMBLE` was a bare module constant with "elf" hardcoded, so a host that named their agent "Theo" still got "answer as elf" on every identity render. The tell that this was a real bug (not just underdocumented) rather than an unstated expectation: the CLI flag and config field's own doc comments described a real, tested, user-facing promise — fixing the code was correct; writing docs that said "expect this contradiction" would have been documenting a bug instead of resolving a legitimate need. General check before accepting "it's already wired" as an explanation for surprising behavior: trace the literal hardcoded value hop-by-hop to its render site rather than trusting that the config field being used *somewhere* means it's used *everywhere* it should be.

## When a bug fix's correct default is silent/backward-compatib
<!-- id: 390adac0952e8a8f  tags: [design/migration, bug-pattern, self/constraint]  pinned: false -->
cue:: a bug fix's correct default is backward-compatible/silent; deciding whether a fix alone is sufficient or needs a migration step; wiring a destructured tuple return from a function read earlier in the session

When a bug fix's correct default is silent/backward-compatible (agent_name falling back to "elf" unchanged), the fix alone doesn't close the gap for existing projects — they stay on the old behavior forever with no signal a choice exists. The right follow-up is a migration step that makes the implicit default an explicit, recorded fact: offer to set it, default to the same value the silent fallback already produced, but write it to config so it's no longer invisible. Two implementation notes worth keeping: (1) reuse the exact three-way non-interactive gate (--yes/--dry-run/--json) an existing confirmation prompt already established, rather than inventing a new one — consistency matters more than a tailored condition; (2) I caught a real bug (`_resolve_migrate_paths` returns `(config, db)`, I destructured it as `(db, config)`) only by re-reading the actual `return` statement rather than trusting my memory of a function I'd read minutes earlier in the same session — worth the extra grep every time on tuple-returning functions before wiring a destructure.

## When a bug report includes a measured claim, reproduce the m
<!-- id: 1dee00464be23015  tags: [bug-pattern, design/api, self/constraint, pattern/verification]  pinned: false -->
cue:: a bug report cites measured numbers; deciding whether to trust a reporter's stated mechanism; shipping a filter change to a frame or query path that live instances already depend on

When a bug report includes a measured claim, reproduce the measurement before designing the fix — the mechanism is often different from what was reported, and the difference changes the remedy. A downstream integration reported elfmem's ScoredBlock.similarity as "min==0.0 on every multi-block recall, relative within one recall". Measured on a real corpus it was min=0.905, max=1.0. Two independent mechanisms, not one: 0.0 is a SENTINEL for "vector search never scored this" (queryless frame, or graph-expanded block), and 1.0 is RRF-normalisation compressing values into a narrow band. Their mitigation (0.25 + 0.75*similarity, designed for a 4x spread) therefore yields 1.08x in the RRF band and a uniform weight on queryless frames — the crash was gone but the weighting was inert. Telling them that was worth more than the fix they asked for. Second lesson from the same report: a filter that could break a live frame is safe to ship when an existing precedence rule protects the affected blocks — verify by measuring both corpus shapes (here: byte-identical no-op on a corpus where the tag is broadly applied, corrective on one where it isn't), and state the escape hatch in the migration note.
